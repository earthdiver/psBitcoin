# 下位8ビットをまとめたテーブルの比較

現在は256点方式を `BitcoinWallet.ps1` に採用し、Fast版を削除しています。以下は採用判断時の比較記録です。

計測日: 2026-09-11。変更前の256点方式（v1）と、下位8ビットだけをまとめた503点方式（v2）を同じ条件で再計測しました。

## 実装

- v1: G, 2G, 4G, …, 2^255Gの256点。16,392バイト。
- v2: G〜255Gの255点と、2^8G〜2^255Gの248点。合計503点、32,200バイト。
- v2では最下位バイトで最初の点を選び、残りの248ビットはv1と同様に処理します。0Gは保存せず、下位バイト0なら初期点なしで開始します。
- どちらも初回使用時に生成またはファイル読込を行い、その後は同一セッションのメモリを再利用します。

## 計測条件

- Windows PowerShell 5.1とPowerShell 7を順番に実行し、同時に他のテストは動かしていません。
- 01〜07の各例について、新旧方式を交互に実行。順番は試行ごとに反転します。
- 初回生成と保存済みテーブル読込をそれぞれ3回、新しいプロセスで測定。同じプロセスで2回目も測定します。
- 以下の「メモリ」は読込条件での2回目の中央値です。生成条件での2回目もJSONに保存しています。
- 単位はミリ秒、各条件3回の中央値。プロセス起動・ライブラリ読込・出力検証・画面描画は除外しています。
- 全出力は.outと照合。ソース・単語リスト・キャッシュはローカル一時ディレクトリを使います。OSのファイルキャッシュはクリアしていません。
- 01と05は固定基点乗算を使いません。この2例の差をテーブル方式の効果とは解釈できません。

```powershell
./tests/Benchmark-GeneratorVariants.ps1 -BaselineRoot <256点版を保存したディレクトリ> -Repetitions 3
```

新旧の[実装差分](generator-low8.patch)と、[全測定値・ソースのSHA256](generator-low8-2026-09-11.json)も保存しています。実装差分を現在の256点版の比較用コピーへ適用すると、試験した503点版を再現できます。比較ツールは両ディレクトリの `BitcoinWallet.ps1` を実行します。

## 結果の読み取り

- 固定基点乗算を使う02・03・04・06・07は、両環境ともv2の初回生成がv1より遅くなりました。
- メモリ再利用時の改善は環境・例で揃いません。5.1の03は9.2%短縮しましたが、7.6.5では0.7%でした。7.6.5の04は18.0%短縮しましたが、5.1では2.4%遅くなりました。
- したがって、下位8ビットの変更だけで安定した全体高速化が得られたとは判断できません。テーブルサイズは約1.96倍となり、初回の負担も増えています。
- ランダムなスカラーで下位8ビットの点加算が減る回数は平均約3回です。上位248ビットは従来どおりなので、削減範囲は限定的です。
- 全336回の例の出力が.outと一致しました。別途、PowerShell 5.1・7の全スイートでも新規失敗はなく、既知のパイプライン問題32件だけが残っています。

比較後、256点版を `BitcoinWallet.ps1` として採用し、`BitcoinWalletFast.ps1` は削除しました。503点版は再現用の差分として保存しています。
